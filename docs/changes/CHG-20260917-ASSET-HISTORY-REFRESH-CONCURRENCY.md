# CHG-20260917：UV/拓扑历史远端刷新并发稳定性

## 1. 问题与证据

- 实际现象：`GET /api/history?module=uv|retopology` 会对最多 100 条非终态记录直接执行 `Promise.all`；每个调用最多等待远端 2.5 秒。多个用户或同一用户多个标签页同时读取历史时，远端查询数按“请求数 × 活动任务数”放大。
- 期望结果：同一用户同一 Job 的同时刷新只请求一次；进程总并发和单用户并发均有硬上限；远端慢或不可用时仍返回持久历史，不阻塞其他用户。
- 证据：`apps/server/src/routes/history.ts` 的 `refreshedAssetHistory()` 对 `initial` 直接 `Promise.all`，没有共享在途任务或跨请求并发门禁。

## 2. 范围

- 变更等级：L1。
- 主模块 ID：`M13` Cloud 控制面稳定性。
- 影响模块 ID：`M10` 生产 UV/拓扑服务、`M15` 回归门禁。

- 明确不做：不减少历史 limit，不隐藏失败记录，不修改远端 Asset API、任务状态含义、产物、ownership、PostgreSQL/本地持久化或前端。

## 3. 当前契约与根因

- 当前输入：已认证用户、`uv|retopology`、1–100 limit，以及账号持久化的任务历史。
- 当前输出：按用户隔离的持久记录；远端刷新失败时保留旧记录。
- 根因：并发仅存在于单次 `Promise.all`，没有按用户公平的进程级调度，也没有相同 Job 的 in-flight 合并。

## 4. 方案

- 进程级刷新上限 8，单用户上限 4；排队时跳过已达单用户上限的任务，使其他用户可使用剩余槽位。
- 以 `userId + jobId` 合并同时在途刷新，完成或失败后删除 in-flight 条目。
- 单次历史请求等待刷新最多约 2.75 秒；预算结束后返回当前持久记录，排队任务继续在有界协调器中完成。
- 远端失败仍吞掉刷新错误并保留原持久记录；不猜测 mode，不改变终态判断。
- 数据或版本升级：Patch；无 Schema 或数据迁移。

## 5. 风险与回退

- 主要风险：等待预算结束时部分排队 Job 的最新状态可能在下一次历史读取才可见。
- 性能影响：进程最多 8 个、单用户最多 4 个远端状态请求；in-flight Map 只在任务排队/执行期间持有 Promise，完成后删除。
- 回退：恢复路由内直接 `Promise.all` 并删除协调器；历史数据无需改写，但会重新引入远端请求风暴。
