## 证据与根因边界

- 本地实际 ViewportCanvas 两层 4K 基线首次反馈 745ms：完整 UV 合成 578ms，显示上传 108ms。主要成本仍是整图光栅、Top-3 回读、CPU/Worker 后处理和 gutter。
- ResidentProjectedUvDisplay 虽调度交互任务，但源纹理上传与最终显示上传均未传 allowWhileInteracting，仍可能等待全局交互静默。
- 正常绘制事件在 capture 阶段 stopImmediatePropagation，可能不会触发相机的全局 busy；因此不能把这个门禁断言为用户每一次松手才更新的唯一根因。
- Modddif 录屏仅证明交互表现，不证明内部渲染架构。

## 实施

1. allowWhileInteracting 从派生交互显示显式透传到 UV 源纹理上传及颜色/R8 结果上传；只有交互草稿为 true。保留分条预算、取消检测、GL 状态恢复、资源释放和完整上传后发布屏障，未全局关闭相机保护。
2. 交互结果 ImageData 的 RGBA buffer 转移至既有预览 Worker；沿用 R8 的有界逐行分条机制，支持四通道。结果没有持久缓存消费者，转移后调用者不得再访问 buffer。非交互结果仍走旧 ImageBitmap 路径，保证压缩缓存可继续读取原图。
3. Worker 保留原始 RGB/Alpha 字节并做与旧路径一致的 Y 翻转，上传依据纹理格式选择 RED/RGBA。R8 仍复制一份、不转移调用者蒙版；RGBA 转移其独占结果。取消/失败仍由原 worker release 与 stripe 清理逻辑处理。
4. 测试从“按下等一下，再移动等一下”扩展为 60 次持续移动，检查移动期间已有多次输出；新增强制 busy 模式与仅在隔离 Vite 中恢复旧门禁的反证开关。
