# Li3D 零组件云端版验收汇总（2026-08-22）

## 1. 验收结论

当前 `codex/modernization` 分支已经形成可部署、可回滚、可继续压测的零组件候选版本：用户只需浏览器，不需要下载或启动 Li3D 本地组件；账号、项目文档、资产元数据、任务历史和正式交付物均由服务器按账号保存；浏览器交互渲染和浏览器计算仍消耗每位用户自己设备的 CPU/GPU；AIGC、正式 UV/拓扑、正式 Substance 烘焙则按产品边界提交给独立计算服务。

这不是“全部计算都塞进网页”或“全部计算都压到 Li3D Web 服务器”的方案。正确边界如下：

| 能力 | 实际执行位置 | Li3D Web 服务器职责 |
| --- | --- | --- |
| 3D 视口、相机、材质预览、图层交互 | 用户浏览器 GPU | 下发静态前端和项目数据，不参与逐帧渲染 |
| 贴图合成、PNG 编码、蒙版、部分投影/烘焙内核 | 用户浏览器 Worker、OffscreenCanvas、WASM、可用时的 WebGPU/WebGL | 保存结果，不承担用户本地帧循环 |
| AIGC 生图 | 独立 GPU/AIGC 服务 | 鉴权、提交、轮询、回调、历史与资产归档 |
| 局部重绘 | 独立 ModelView 服务 | 鉴权、任务编排、结果归档 |
| 正式 UV 与拓扑 | 独立 Asset V4 服务 | 传输模型、校验 SHA-256、任务历史和交付物归档 |
| 正式 PBR 烘焙 | 独立 Substance Bake 服务 | 提交高低模/贴图、轮询、归档输出 |
| 项目与工作区 | PostgreSQL + S3/MinIO 对象存储 | 账号隔离、版本冲突保护、对象元数据和下载授权 |

因此，100 名用户打开编辑器时，100 份交互帧循环分别运行在 100 台用户设备上，不会把 Li3D Web 服务器当作远程桌面或共享 GPU。服务器主要承担 API、数据库、对象存储签名和任务调度；真正的集中式 GPU 工作由独立 AIGC 服务集群承接。

## 2. “没有本地组件”的代码证据

1. 浏览器前端通过同源 `/api` 使用 HTTP/JSON、Cookie 会话和对象存储上传，不连接 localhost 守护进程、命名管道或本机专用端口。
2. 云端项目保存不再检查或创建“本地工作区”；云构建直接写服务器项目仓库和对象存储。
3. 模型、参考图、缩略图和生成结果在 HTTP 非安全来源下不再依赖 `crypto.randomUUID()` 或仅 HTTPS 可用的 `crypto.subtle`。ID 有浏览器兼容回退；SHA-256 在 SubtleCrypto 不可用时使用等价的浏览器实现；大文件通过服务器代理写入 S3/MinIO。
4. 前端没有“下载 Li3D 本体组件”作为贴图、UV、烘焙的前置条件。DCC/Photoshop 工具被明确列为独立可选工具，不属于网页核心功能依赖。
5. `/api/comfyui/*` 旧接口、服务端实现、前端客户端和旧取消冒烟脚本已从生产代码移除。`GET /api/comfyui/status` 的验收结果应为 `404`，用于证明旧链路没有被误挂回生产服务。

需要注意：仓库中的历史变更文档可能记录过去的 ComfyUI 或本地挂载方案，它们仅是历史资料，不代表当前生产架构。

## 3. 浏览器图形引擎与 D3D 说明

核心 3D 层使用 React Three Fiber + Three.js `WebGLRenderer`。视口、模型预览、投影、GPU RenderTarget 和像素回读均在浏览器进程执行。CPU 密集型图像操作通过 Web Worker、OffscreenCanvas 和 WASM 分离，避免堵塞 UI 主线程；支持条件满足时，部分合成内核可选择 WebGPU，否则使用 WebGL/CPU 回退。

Web 应用不会直接调用原生 D3D API。在 Windows Chromium/Edge 的默认配置下，WebGL 通常由 ANGLE 翻译到 D3D11；实际后端也可能因操作系统、浏览器、驱动、企业策略或启动参数变为 D3D12、OpenGL、Vulkan 或软件渲染。因此准确表述是：

- Li3D 使用浏览器 WebGL/WebGPU 安全接口；
- Windows 上通常经 ANGLE 使用用户本机 D3D；
- 最终后端必须以目标浏览器运行时的 `WEBGL_debug_renderer_info`、WebGPU adapter 或 `chrome://gpu` 为准，不能在服务器端硬编码宣称 D3D11；
- 服务器健康信息明确报告 `browserLocalGraphics: true`、`serverGraphicsFallback: false`。

这也解释了为什么服务器部署在 A100 主机上，不代表每个编辑器视口在使用 A100：静态网页加载到用户浏览器后，逐帧图形命令在用户设备执行；只有明确提交到 AIGC/资产/烘焙 API 的任务才进入远端计算服务。

## 4. 数据归属、账号隔离与多用户架构

账号会话来自真实飞书/莉刻 OAuth 登录。服务端以不可伪造的稳定用户 ID 作为所有权主键，不以界面显示姓名作为隔离依据。以下对象均绑定账号：

- 项目、文件夹、项目版本与项目文档；
- 模型、参考图、贴图、缩略图和任务交付物；
- UV、拓扑、烘焙、生成和局部重绘历史；
- OAuth 会话、用户设置和一次性登录 state。

PostgreSQL 保存结构化状态和不可变项目 revision；S3/MinIO 保存大二进制对象；下载走鉴权后的对象授权。更新请求携带 revision，过期写入返回 `409`，防止两台设备或两个副本静默覆盖彼此修改。服务端可以横向扩展为多个无状态应用副本，共享 PostgreSQL 和对象存储。

### 100 用户证据与边界

- 回归验收：100 个账号、8 个应用副本，验证项目、会话、OAuth state、文件夹、历史、对象元数据和设置严格隔离，并验证重启恢复。
- PostgreSQL 浸泡：4 副本、4 账号、15 轮、240 次重试，包含事务回滚注入和重启恢复。
- A100 实机并发：单个真实登录会话、100 并发连接、15 秒，共 74,196 次请求，失败 0，约 4,930 RPS，P50 11.7 ms、P95 63.3 ms、P99 82 ms。

必须如实区分：实机并发测试证明 API 在 100 并发连接下没有被拖垮；100 个不同账号的所有权隔离由自动化多账号/多副本测试证明。正式上线前仍应使用生产 IdP 测试账号、生产级 PostgreSQL/对象存储、网关限流和 30～60 分钟混合负载再做一次发布门禁。

## 9. 2026-08-23 增量收尾

### 9.1 A100 生命周期修复

2026-08-22 首次真实部署使用手工 `nohup`，SSH 生命周期结束后 44770 无进程监听，用户看到 `ERR_CONNECTION_REFUSED`。现已安装并启用系统级 `li3d-modernization.service`：

- 开机自动启动；
- 异常退出 3 秒后自动重启；
- 主动 `SIGKILL` 后 PID 从 `392844` 切换为 `392868`，状态恢复 `active/running`；
- 退出 SSH 后外部端口、页面、readiness 仍正常；
- 详细操作和回滚见 [A100 真实服务器部署与运维交接](A100_SERVER_HANDOFF_2026-08-23.zh-CN.md)。

实机同时发现根分区利用率达到 95%，这是当前生产阻断项；应用发布不得自行删除共享服务器数据。

### 9.2 CI/CD 失败与修复

提交 `dcd0eb9` 的功能、类型和回归测试均通过，失败发生在 build 阶段的前端包预算：应用壳为 267,610 B，超过 265,000 B 门槛 2,610 B。修复采用按需加载而不是放宽预算：

- 文件上传发生时才加载 SHA-256 的 HTTP 兼容实现；
- 身份状态关联和遥测在首屏渲染后按需加载；
- 新构建应用壳为 260,240 B，预算门禁通过；
- SHA-256、身份和遥测成为独立 chunk，原有功能未删除。

### 9.3 第二轮原版对齐

发现原版新人引导组件和六步引导内容仍在，但云端新建项目只依赖 `createdAt` 的 30 分钟判断，入口没有显式表达“这是刚创建的贴图项目”，因此部署时间、恢复和路由状态变化可能导致引导不出现。

现已改为：

1. 新建贴图项目成功后显式传递 `showOnboarding`；
2. App 路由把该意图交给编辑器；
3. 编辑器以 `forceStart` 启动原版同一套六步引导；
4. 直接刷新/深链仍保留 `createdAt` 与本地进度恢复逻辑；
5. 新增回归门禁，防止项目创建、路由、编辑器和引导组件之间再次断线。

隔离云端模拟器已完成真实浏览器交互复验：OAuth/PKCE 授权、Cookie 会话、新建贴图项目均成功；创建后编辑器自动显示原版第一步“导入模型”，无需下载组件或打开本地工作区。模拟器同时完成直接对象上传、首次 503 重试、幂等命令、优雅停止和重启数据恢复。

二次差异审计还确认：账号菜单中删除“本机莉刻账号绑定”、首页/工具箱删除安装器、PS/DCC 操作暂缓、历史改为账号级服务器记录，均是零组件需求的有意差异，不能为了像素复制重新引入本地组件。必须保持原版一致的是可见功能、工作流、引导、工具清单、项目恢复和交互语义；允许不同的是执行位置、持久化实现和被明确暂缓的本机桥接入口。

### 9.4 UV 历史传入烘焙的并发修复

真实服务器复验发现，历史任务右侧“传入烘焙”可能在项目已被其他请求推进后，继续提交页面内缓存的旧快照，触发 `Blocked saving a stale project snapshot over newer project data`。服务端拒绝是正确行为；问题位于网页交接逻辑没有对齐最新 revision。

现已改为以服务器最新项目为基线，增量合并本次任务新增的 pipeline revision、模型资产和 Bake Set，并保留 `expectedRevisionId` 乐观并发控制。浏览器提交时间也必须严格晚于服务器最新 `updatedAt`，用于兼容浏览器时钟落后和重试窗口；不降低服务端的 revision 与时间戳双重防覆盖保护。只对 409 冲突重新读取并重放，最多三次；不会覆盖其他页面、其他任务或同账号并行操作刚写入的数据。完整门禁增至 33 条网页回归，且云端模拟器继续通过登录、直接上传、冲突重试、幂等、优雅关闭和重启恢复验证。
