## 1. 优化目标

本轮优化将视口交互帧作为最高优先级，覆盖模型旋转、平移、缩放以及 UV 合成、内容修补、投影深度生成和纹理上传并发执行的场景。

约束如下：

- 后台任务不得长时间阻塞浏览器主线程或独占 GPU。
- 用户操作视口时，后台任务必须在安全边界暂停。
- 不降低 1K、2K、4K、8K 用户选择的纹理分辨率。
- 不减少图层、不降低采样质量、不改变最终内容结果。
- 保持 UV 合成、投影图层和内容修补显示正确。

## 2. 核心问题

优化前的卡顿来自多条任务链路同时抢占帧预算：

1. 4K UV 合成包含大尺寸离屏渲染、GPU 像素读取和纹理上传。
2. GPU 同步等待可能让 JavaScript 主线程等待显卡完成工作。
3. 多个投影图层重复遍历同一份模型几何数据。
4. 内容识别拓扑构建包含密集数组分配和连续循环。
5. React 图层列表、性能遥测与后台预热会和视口交互竞争。
6. 部分后台步骤本身超过一帧预算，即使步骤之间异步仍会产生长帧。

因此，本轮通过交互抢占、任务分片、缓存复用和消除同步等待解决问题，没有通过降低质量换取帧率。

## 3. 已完成的优化

### 3.1 统一视口交互优先级

- 增加统一的视口交互状态和空闲等待机制。
- 旋转、平移或缩放开始后，UV 合成、纹理预热、深度生成和拓扑计算会在安全边界暂停。
- 连续安静约 180 ms 后，后台任务自动恢复。
- 暂停不会丢弃中间结果，也不会让任务从头重新计算。

主要文件：

- `apps/web/src/engine/viewport/viewportInteractionState.ts`
- `apps/web/src/routes/EditorPage.tsx`

### 3.2 GPU UV 合成分块与异步化

- 大尺寸离屏渲染改为 768 px 分块。
- GPU 像素读取改为约 4 MB 的条带式读取。
- 每帧限制一次高成本 readback，避免连续读取堵塞渲染管线。
- 交互期间采用约 4 ms 的后台工作预算，达到预算后让出呈现帧。
- 修复异步等待后 framebuffer 状态丢失，恢复后重新绑定正确目标。
- 每个安全边界都会重新检查用户是否正在操作视口。

主要文件：

- `apps/web/src/engine/bake/gpuUvBakeRenderer.ts`
- `apps/web/src/engine/bake/bakeProjectedLayerToTexture.ts`

### 3.3 消除 GPU 同步等待造成的长帧

实测发现 NVIDIA 驱动环境中的 `clientWaitSync` 即使使用零超时，也可能让主线程阻塞约 134–150 ms。

处理方式：

- 移除可见纹理上传路径上的同步 GPU fence 等待。
- 利用同一 WebGL 上下文的命令顺序保证上传正确性。
- 纹理上传完成后等待两个呈现帧再发布，避免显示半成品。
- 可见纹理使用约 0.5 MB 条带，后台纹理使用约 2 MB 条带。
- 用户开始交互时，在当前条带结束后立即暂停后台上传。

主要文件：`apps/web/src/engine/viewport/previewTextureCache.ts`

### 3.4 投影深度与捕获任务分片

- 深度和法线捕获使用 256 px 小块处理。
- 捕获任务使用约 4 ms 单帧预算，超出后等待下一次呈现。
- 给模型几何签名增加微任务周期缓存，避免 14 个投影图层重复遍历顶点。
- 运行时深度生成可以在交互开始时暂停并安全恢复。

主要文件：

- `apps/web/src/engine/capture/renderTargetUtils.ts`
- `apps/web/src/engine/projection/createRuntimeProjectionDepth.ts`

### 3.5 内容识别拓扑构建调度

- 将几何遍历、数组分配和拓扑构建拆成可让出的阶段。
- 交互期间通过动画帧与定时器联合调度，优先完成视口呈现。
- 空闲期间继续高速处理，不永久降低算法速度。
- 修补像素数和 checksum 多轮测试保持一致。

主要文件：`apps/web/src/engine/contentAware/buildSurfaceTopology.ts`

### 3.6 React 图层面板更新降噪

- 图层可见性和渲染器状态仍然立即生效。
- 仅把非关键 React 列表刷新在交互期间延迟约 32 ms。
- 避免大量图层的 DOM 更新抢占旋转、缩放和移动帧。

主要文件：`apps/web/src/components/panels/LayersPanel.tsx`

### 3.7 后台预热策略

- UV、投影纹理和内容修补预热不再允许在视口交互期间强行执行。
- 用户停止操作后自动恢复，最终质量处理不会被取消。
- 避免预热、解码和 GPU 上传在同一帧集中发生。

### 3.8 性能实验室与诊断

- 交互期间跳过非必要的性能遥测，避免测试工具本身制造掉帧。
- 增加 GPU 阶段、长动画帧、纹理发布、深度生成和修补阶段指标。
- S4 UV 合成测试加入开始阶段和处理中途两段自动旋转。
- S9 内容修补测试加入初始、深度生成中途和拓扑构建中途三段自动旋转。
- 分开统计受保护交互帧和完整后台流程，避免平均值掩盖卡顿。

主要文件：

- `apps/web/src/engine/viewport/ViewportCanvas.tsx`
- `apps/web/scripts/test-projected-layer-visibility.mjs`

## 4. 质量与逻辑边界

本轮性能修改没有：

- 降低纹理分辨率或 UV 采样质量。
- 减少投影图层数量。
- 修改 PBR 光照写入逻辑。
- 修改 Blend/Overlay 混合公式和显示语义。
- 改变内容识别修补的最终计算结果。

性能收益来自后台任务分片、交互抢占、缓存复用、GPU 状态修复以及移除同步等待。

### 5.2 S4 UV 合成并发交互

- 处理期间包含两段自动旋转。
- 受保护交互帧：P95 16.8 ms，最大 16.9 ms。
- GPU 总处理约 73.2 秒，其中运行时深度约 42.9 秒、GPU 读取约 26.0 秒。
- 输出约 16.24 MB，WebGPU A/B 最终结果差异为 0。
- 未检测到 JavaScript 主线程长任务。

完整后台阶段观测到一次 33.5 ms 的浏览器合成器漏同步。它发生在无交互的后台上传阶段，两段主动旋转窗口均保持稳定，且该帧没有对应的 JavaScript 长任务。

### 5.3 S9 内容修补并发交互

- 总耗时约 26.7 秒，包含三段自动旋转。
- 14 个投影图层参与处理。
- 修补像素数：926,179。
- 稳定校验值：`766711066` / `#2db3151a`。
- 三段旋转均为 P95 16.8 ms、最大 16.8 ms。
- 完整流程为 P95 16.8 ms、最大 16.9 ms、0 掉帧。
- 投影材质重建次数为 0。
- 原始图层恢复、底图安全性、纹理就绪和最终可见性全部通过。

GPU 诊断存在 15 个 RGB 字节的 1 级差异和 2 个 Alpha 字节差异，属于 GPU 精度尾差；最终修补像素数与 checksum 完全一致。

### 5.4 刷新恢复

- 总恢复时间约 10.65 秒。
- 15 个图层和 14 个投影图层全部恢复。
- UV 预热约 7.59 秒，最大主线程长任务为 0。
- 多轮压力测试后刷新，JavaScript 堆从约 3.5 GB 回落至约 1.5 GB。
