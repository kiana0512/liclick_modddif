# Li3D 性能优化阶段 6：驻留、提交调度与独立 GPU 光栅路线

更新时间：2026-08-07（局部重绘遮挡、内容修补与 S6 回滚迭代）

## 1. 优先级和边界

阶段 6 继续遵循固定优先级：

1. 交互稳定，主视口持续出帧；
2. 4K 输出和投影质量不降低；
3. 在前两项成立后缩短完成时间。

任何优化只要改变 4K 覆盖、alpha、颜色或可见性判定，即使更快也直接撤回。CUDA 只可作为 Windows/NVIDIA 的可选原生后端；默认路径仍采用 Worker、WebGL2 和 WebGPU，兼容 Intel、AMD 与 Apple Silicon。

## 2. 本轮已经落地

### 6.1 合成 UV 的 GPU 驻留缓存

- `SceneRoot` 为已经完成的 UV 合成纹理建立容量为 3 的 LRU。
- UV/投影切换命中相同图层签名时，直接复用显存中的完整纹理，不再重复执行 `createImageBitmap -> Worker 合成 -> GPU 上传`。
- 空 UV 栈只关闭显示，不立即销毁最后一张正确纹理；替换和淘汰延迟两个显示帧释放，避免采样中的纹理被销毁而产生黑闪。
- 缓存命中记录为 `resident-gpu-cache`，不改变纹理尺寸和像素。

### 6.2 投影数组的细粒度 GPU 提交

- 投影数组仍按原预览分辨率生成，但上传被拆成每次最多约 1 MiB RGBA 的 `texSubImage3D` 条带。
- 每条上传前把一个显示帧让给视口；交互保护开启时等待，不与拖拽旋转抢占主线程和共享 GPU 队列。
- 四类数组继续使用“Worker 并行准备、GPU 串行上传”，取消任务不会发布半成品。
- 增加显存分配、上传总耗时、最大条带耗时、着色器编译耗时和 yield 次数埋点。

### 6.3 着色器程序驻留

- 大容量投影材质离开场景时立即释放其数组纹理，但保留最多 3 个不持有纹理的已链接 ShaderMaterial 锚点。
- Three.js 因此不会在 0→14、UV/投影切换和测试栈恢复时释放最后一个相同 WebGLProgram 引用。
- 本机 14 层材质再次使用时，编译耗时由 `186.3ms` 降至 `0.1ms`；缓存有严格容量，不会随操作次数增长。

### 6.4 运行时深度 GPU 队列

- 同一个 WebGLRenderer 上的深度/几何法线捕获进入严格串行队列。
- 防止多个视角的异步 readback 和材质切换交错修改共享 R3F 上下文。
- 分辨率、深度编码、法线算法和 PNG 数据路径保持不变。

### 6.5 独立 Worker WebGPU UV 拓扑光栅（首个生产切片）

- 新增 Worker 自有的 WebGPU `render pipeline`，UV 三角形一次性光栅到完整 4K `r8unorm` 纹理；不使用 R3F/WebGL 上下文，也不做图像分片。
- 主线程只负责模型首次序列化，且每 8192 个顶点主动归还事件循环；pipeline、device、GPU buffer、render target 和 readback 全部在 Worker 内完成。
- 首次模型/分辨率组合在 Worker 内与 OffscreenCanvas 金标准逐像素校准。工业机器人 4K 原始边缘差异为 11838 像素，稀疏校准后最终差异为 0；后续复用缓存结果，不再扫描模型或主线程 Canvas。
- WebGPU 不可用、device 丢失、Worker 异常或最终差异非 0 时不发布 GPU 候选，自动回退 Worker Canvas，再保留原主线程兼容实现作为最后保险。
- `?webGpuUvTopology=0` 可显式关闭该切片，用于兼容性回归。性能实验室新增“S4 WebGPU 拓扑光栅”卡片，显示后端、耗时、校准像素与最终差异。

### 6.6 局部重绘实时 GPU 前景通道

- 局部重绘颜色源和 Alpha 蒙版保持为两张独立 GPU 资源；颜色直接使用生成图原始分辨率，当前实测为 `2048×1032`，交互蒙版为 `1024px`，不再使用 512/288 低清代理。
- 生成结果出现后后台完成图片解码、纹理上传、空蒙版上传和 shader/material 预编译；后台阶段不会自动切换工具。按钮 3 只检查 ready 标记并原子切换，未完成时复用进行中的任务，不重新解码。
- 实时局部替换作为独立 GPU 前景 sampler，永远不进入 14 层背景纹理数组重打包；因此既保留原始清晰度，也避免首笔/停笔触发整组数组上传。
- 混合语义改为“蒙版内字面替换”，不再采用改变对比度的 Overlay 效果。持久化继续保存高清源图与透明 Alpha，不创建黑底或整幅 RGBA 中间图。
- 图层缩略图和大图预览都应用实际 Alpha；大图使用棋盘格透明背景，便于核对实际替换区域。
- S6 测试器与产品规则统一：只允许空白 UV 或局部重绘专用 UV 作为目标，并独立显示“按钮 3 GPU ready / 首笔可见”指标。

### 6.7 局部重绘冷启动、进度与即时删除

- 生成结果不再先转为 base64 data URL。浏览器直接解码原始资源地址，消除一次完整下载、字符串扩容和主线程字节复制。
- 已解码的 2K/4K 图片直接注册为 GPU 前景纹理，不再为了进入实时材质而复制到同尺寸 2D Canvas；透明 Alpha 仍由独立蒙版纹理控制，像素质量不变。
- 删除固定 5 秒等待和超时后重启预热的逻辑。纹理解码、颜色上传、Alpha 上传、材质编译完成后立即发布 ready；仅在实际未完成时等待，不人为延长白膜时间。
- 复用顶部进度条展示“读取高清结果 → 解码蒙版 → 上传颜色 → 上传 Alpha → 编译材质 → ready”，避免用户在资源尚未就绪时落笔却看不到反馈。
- 预热采用旧材质/新材质双缓冲：新 GPU 资源 ready 前保留最后一个有效材质，避免切换期间退回白膜。
- 删除局部重绘层时先同步把运行时 GPU 可见性置零，下一帧再低优先级移除图层行和释放资源；局部重绘层删除不再把 14 层投影栈标记为需要重新烘焙。

### 6.8 图层混合模式常驻 GPU 状态

- Blend/Overlay 不再属于投影材质结构签名，点击不会触发纹理数组重组或重新编译整套投影 shader。
- 两种模式使用同一常驻 shader 的互斥 uniform，当帧只执行一种合成路径，避免旧 Blend 与新 Overlay 在异步切换窗口中同时存在。
- 本项只改变运行时状态调度；投影覆盖阈值、视角判定、深度/法线判定、edge feather 和 Overlay 原颜色/Alpha 公式均保持不变。

### 6.9 局部重绘前表面遮挡与图层可见性

- 按钮 1 的屏幕投影蒙版为每个相机投影保存一张 `512px`、RGBA packed 的前表面深度；实时蒙版 shader 和最终蒙版捕获 shader 都比较投影 NDC 深度，遮挡后的片元直接丢弃。因此从模型背面画选区时，不再同时写到前面或内部零件。
- 深度轮廓使用中心 texel 加上下左右四个最近 texel 的保守判断，处理非抗锯齿深度轮廓的小缝；分辨率、模型三角形和最终 1K/2K/4K/8K 纹理质量均未降低。
- 对象移动后使用对象矩阵和法线矩阵增量更新深度/法线判断，避免投影快照只在模型初始姿态正确。
- 深度 render target 保留并复用；`MeshDepthMaterial` 在组件生命周期内常驻，不再在每次首笔后 `dispose` shader program。工业机器人 S6 的按钮 1 首笔最大帧由 `143.9ms` 降到 `18.2ms`。
- 局部重绘实时 GPU 覆盖树不再无条件可见。对应持久图层的 `visible` 是唯一真值：眼睛关闭/打开同步控制普通图层和实时覆盖层，删除不是隐藏生效的必要条件。
- S6 作为诊断事务运行：成功、失败和超时都会恢复完整图层数组、活动图层、局部重绘源/预览、蒙版设置与工具。实测测试前后 18 个图层逐项一致，残留局部重绘测试层为 0。

### 6.10 内容识别修补的结构角桥接与重复 4K 缓存

- 普通表面连通仍使用严格法线阈值 `dot >= 0.72`；只有真实共享几何边的显式 seam link 可使用 `dot >= -0.12` 的结构角桥接。修补核心最多跨越一次 seam，防止颜色沿相邻岛链无限串色。
- donor 继续使用源区域锁定、颜色离群拒绝、源 padding、四邻域传播和 coverage skirt；结构角桥接不会覆盖已有投影，也不会把黄色机身颜色传播到金属滑槽。
- 拓扑采集明确排除局部重绘覆盖层、选择高亮、线框和视口 helper。同一机器人不再因为实时 GPU 覆盖树而从 1 套表面错误膨胀为 2 套。
- 修补分辨率严格跟随顶部 `1K/2K/4K/8K` 选项；上限为 8192，不使用内部 2K 降级。
- 同一项目、对象、分辨率和投影图层签名复用不可变投影证据；每轮只协作式复制证据，再叠加之前的稀疏修补层。任何图像、蒙版、相机、对象矩阵、可见性、强度、混合或颜色调整改变都会使缓存失效。
- 大 RGBA/拓扑数组、拓扑构建和 gap scan 只在下一可见帧之后继续，避免多个 8ms 片段在一次 rAF 前连续运行。
- 4K 工业机器人质量回归：首轮扫描 `2,432,622` 个缺口并修复 `2,284,554`，保留 `148,068` 给下一有界轮；后续项目状态扫描 `3,695` 个剩余缺口并全部修复，下一轮为 0 缺口。显式 seam 数保持 `109,764`。
- 4K 缓存命中轮实测约 `1.15s`，旋转窗口 P95 约 `18.1ms`；首次冷证据生成仍约 `23.68s`、P95 `35.5ms`，尚未达到稳定门槛，不能把缓存热轮当成冷启动通过结论。

## 3. 4K 实测

测试对象：工业切割机器人，14 个真实投影图层、内容识别修补层和 4K UV；硬件为 Intel Core i7-13700KF、NVIDIA RTX 4070 Ti SUPER；屏幕 60Hz。

| 场景 | 交互保护 P95 / 最大 | 松手发布 P95 / 最大 | 结论 |
| --- | --- | --- | --- |
| S1 0→14，三轮 | 16.8 / 16.8–16.9ms | 16.8 / 66.6–66.7ms | 旋转窗口通过；发布仍有单次尖峰 |
| S2 14 层连续开关 | 16.8 / 16.8ms | 16.8 / 50.0ms | 交互窗口通过 |
| S3 修补开关 | — | 16.8 / 83.5ms | 无黑模；发布尖峰未清零 |
| S5 UV/投影切换，三轮 | — | 16.8 / 66.8–83.5ms | 重复 4K 合成已消除；首次提交仍需继续优化 |
| S4 4K 合成 | 33.4 / 183.5ms | — | 质量通过，稳定性未通过 |
| S6 完整局部重绘 | 16.8 / 16.9ms | 16.8 / 66.7ms | 按钮 3 ready 8.8ms；首笔可见 122.4ms；连续反馈 16.2 / 16.3ms |

本轮局部重绘遮挡/常驻材质复测（同一硬件、4K、自动旋转）：S6 交互 P95/最大 `18.1 / 18.2ms`，连续反馈 `17.3 / 17.5ms`，交互窗口没有 >20ms 帧；停笔约 3 秒后的发布窗口仍有 `106.6ms` 最大帧，尚未通过发布门槛。测试事务结束后图层状态完全恢复，局部重绘残留层为 0。

S6 质量复核：来源图保持 `2048×1032` 原始像素，局部替换层只显示自动笔刷覆盖区，区域外 Alpha 为透明；模型视口无黑底、无整图覆盖、无低清雾化。按钮 3 激活与连续笔画已经达到本阶段交互验收目标。停笔约 3 秒后的项目持久化仍可出现 `66.7ms` 单次后台帧，已与实时笔画路径隔离，列入后续项目快照/图层面板虚拟化优化。

S4 金标准：输出 `21.69MB`，覆盖率 `48.20%`；WebGPU A/B 为 `0` 字节差异、最大差值 `0`。阶段耗时：runtime depth `5955ms`、GPU raster/readback `8674ms`、质量混合 `5692ms`。最卡阶段仍是共享 WebGL 的 `gpu-raster-readback`。

独立 WebGPU 拓扑光栅复测：Worker 总耗时 `1035ms`，原始校准像素 `11838`，最终差异 `0`，S4 输出仍为 `21.69MB / 48.20%`。显式关闭 WebGPU 拓扑后，Worker 兼容路径为 `916ms`，输出同样为 `21.69MB / 48.20%`。这证明回退有效，但 S4 交互保护仍只有约 `35ms P95`、最大帧 `408–427ms`，阶段 6 尚未完成；当前最大尖峰转移到 UV underlay 合成/共享 WebGL 深度与光栅链路。

## 4. 被否决的实验

曾尝试把共享 WebGL 的运行时深度/法线捕获拆成 1024 像素 scissor 瓦片，并在瓦片之间归还 R3F renderer。该实验使 S4 覆盖率从 `48.20%` 降到 `3.87%`，同时最大帧仍为 `166.8ms`，因此已完整撤回。浏览器内存中的实验缓存经重新加载清除，项目数据没有被写坏。

本轮还尝试把一次 4K 全幅读回拆成多个 4 MiB PBO 条带。内容修补冷轮由约 `23.68s` 增至 `26.20s`，旋转 P95 仍约 `36.0ms`，没有改善稳定性，因此也已撤回。结论仍是：共享 WebGL 上下文的首次 4K 投影光栅/读回不能靠表面分片解决，必须进入独立 Worker GPU 后端或在上游生成阶段产生可复用证据。

结论：共享 R3F WebGL 上下文不适合继续用“切片 + 伪异步”改造高质量几何光栅。它既难以保证 renderer 状态隔离，也无法真正把 GPU 驱动提交移出 UI 线程。

## 5. GPU 光栅是否能走进实际

能，但必须采用独立后端，而不是继续挤压当前共享 WebGL renderer。

当前已经实际运行的 GPU 路径包括：WebGL2 逐层 UV 光栅、异步 PBO readback、GPU 后处理，以及 Worker 内的 WebGPU Top-K/coverage resolve。尚未进入 WebGPU 的核心是“几何到 UV 的 render pipeline”和运行时深度/法线 render pipeline。

阶段 6 下一切片应建立 Worker 所有的独立 WebGPU device：

1. 主线程只在模型或 UV 改变时传输一次位置、UV、索引和必要矩阵；
2. Worker 建立深度/法线与 UV 光栅 render pipeline，并复用 pipeline、bind group 和 GPUBuffer；
3. 投影纹理进入 `texture_2d_array`，14 层在同一 device 内完成光栅和 Top-K compute；
4. 中间层不回读 CPU，只在最终 4K 结果或导出编码需要时回读一次；
5. 首次启用以 shadow/A-B 模式运行，覆盖、alpha 和颜色达到现有金标准后才接管生产；
6. WebGPU 不可用或设备丢失时，回退独立 Worker WebGL2，再回退当前正确 CPU/共享 WebGL 路径。

这条路线才能同时解决共享 renderer 状态污染、逐层 readback 和 UI 线程 GPU 驱动提交三个问题，并保持跨 Intel、AMD、NVIDIA 和 Apple M 系列兼容。

## 6. 下一轮验收门槛

- S1/S2/S3/S5 交互保护窗口：P95 ≤ 17.5ms，最大帧 < 33.4ms；
- S4：P95 ≤ 20ms，最大帧先降到 < 100ms，再以 < 50ms 为阶段目标；
- 4K 覆盖率与 CPU/现有 GPU 金标准一致；alpha 0 字节差异，RGB 最大差值 ≤ 1，差异比例 ≤ 0.00001；
- 设备丢失、WebGPU 禁用、Intel/AMD/Apple 路径均有明确回退和日志；
- 压测后 GPU 显存与 JS 堆不随测试次数单调增长。
- S6 成功、失败、超时后图层数组、眼睛状态、活动层和工具必须与测试前完全一致；局部重绘测试层残留数必须为 0。
- 内容识别修补冷轮与缓存命中轮必须分开报告；冷轮 `35.5ms P95` 和局部重绘发布 `106.6ms` 仍是当前阻断项。
